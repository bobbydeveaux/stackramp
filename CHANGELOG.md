# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed
- **Faster deploys: only what changed.** Each push deploys only the services whose files changed (per-service dirs, shared dirs, `watch_paths`); a push that touches only docs, markdown, marketing or brand files deploys nothing and skips the scan and quality gate. Prod deploys a service only when its dev deploy ran in the same run (before, every prod service redeployed on every push to main). Manual and scheduled runs, and changes to `stackramp.yaml` or the calling workflow, still deploy everything. Configurable via a new `deploy:` block (`ignore_paths`, `default_ignore_paths`, `full_deploy_paths`).
- **Terraform only when its inputs change.** Provisioning fingerprints its inputs and applies only when they changed (or on `provision: true`, schedule, or a `stackramp.yaml` change); otherwise it reads outputs from state in seconds. Outputs are read with one `terraform output -json` instead of eleven `terraform output` calls per environment.
- **Images built once, in parallel with the scans.** A pre-build job builds each source dir once per commit (an API and a worker sharing a dir share one build) with a BuildKit registry cache in Artifact Registry and Docker Hub pulls via `mirror.gcr.io`; deploy jobs and prod reuse the image. The security scan and quality gate now gate the deploys rather than provisioning and builds.
- **Image tags include a platform fingerprint.** Backend, machine-backend and MCP images are tagged `<commit sha>-<12-char fingerprint>` of the StackRamp build inputs for that image (the `build-image` action and the platform Dockerfile for its language, unless the service has its own Dockerfile). A manual, `deploy_all` or scheduled run on an unchanged app commit now rebuilds after a StackRamp Dockerfile/build change instead of redeploying the stale image; prod still reuses dev's image within a run.
- **Guardian and Pulse run from prebuilt GHCR images** (`ghcr.io/bobbydeveaux/guardian:main`, `ghcr.io/bobbydeveaux/pulse:main`) instead of building their Dockerfiles from Docker Hub images on every run.
- Deploy jobs use the runner's preinstalled gcloud instead of installing the latest each time (~25s per job).
- Machine-backend and Kubernetes prod deploys now also run on `workflow_dispatch` and `schedule` (before: push only), like the other prod deploys.

### Added
- **Preview sweep.** New action `providers/gcp/workflows/preview-sweep` and reusable workflow `_sweep-previews.yml` delete every Cloud Run preview service and Firebase preview channel of the app whose PR is closed. It runs after each PR's own cleanup (which now uses the same action), on scheduled platform runs, and from a daily caller workflow if you add one (see the reference). It only touches the app's own preview services (exact names from `stackramp.yaml` unless labelled for another app, or the new `stackramp-app` / `stackramp-pr` labels on preview services; channels on the dev site from the app's Terraform state), lists before it deletes, keeps previews whose PR state it can't read, and has a `dry_run` mode. Tests: `providers/gcp/workflows/preview-sweep/test_preview_sweep.py`.
- **Platform secrets scoped per app and environment.** Two optional Secret Manager labels narrow which services mount a `platform-inject=true` secret: `platform-app=<app name>` (only that app's services) and `platform-env=<dev|prod>` (only that environment; PR previews count as `dev`). A secret with neither label is mounted everywhere, as before. Discovery now lives in one action, `providers/gcp/workflows/platform-secrets`, used by the backend deploy and migrations job, MCP and machine-backend deploys, and the SSO frontend. A relabel reaches a service on its next deploy; a service left with no matching platform secret (and no `DATABASE_URL`) is deployed with `--clear-secrets` so scoped-away secrets come off it (a project with no platform secrets at all is unchanged).
- Workflow inputs `deploy_all`, `provision` and `dry_run` (report the plan only).
- **IAP user identity forwarding** (#33) — the SSO proxy now forwards the authenticated caller's identity to the backend via two re-keyed pass-through headers, `X-Stackramp-User-Email` and `X-Stackramp-User-Id`, sourced from IAP's `X-Goog-Authenticated-User-*` headers with the `accounts.google.com:` prefix stripped. Backends opt in to user-aware logic by reading the new headers; existing backends that ignore them are unaffected. Re-keying avoids the Cloud Run auth-layer collision that requires the proxy to strip the original IAP JWT headers.
- **GCS bucket support in `stackramp.yaml`** (#34) — the `storage:` key now accepts a block form, `storage.buckets`, that provisions one GCS bucket per entry and injects a `BUCKET_<NAME>` env var into the Cloud Run service (for example, a `downloads` bucket exposes `BUCKET_DOWNLOADS`). The runtime service account is granted `roles/storage.objectAdmin` on each provisioned bucket. The existing scalar forms `storage: false` and `storage: gcs` are unchanged and remain back-compatible; use the scalar form or the block form, not both in one file.

### Fixed
- **PR previews scale to zero.** Preview services (`pr-<n>`) are always deployed with `--min-instances=0` and CPU throttling, ignoring `min_instances` and `always_on` (which now apply to dev and prod only). Before, a backend kept warm for prod (`min_instances: 1`, or `always_on`) kept one instance per open PR running 24/7: 89% of one week's billable Cloud Run instance hours in a shared project were previews. Applies to `_backend.yml` and `_mcp.yml` (the mcp block and `backends:`); preview frontends are Firebase channels and unchanged.
- **No preview after its PR closed.** When a PR was marked ready and merged seconds later, the close cleanup could finish before the ready run's deploy, which then created the preview services again. Preview deploys (backend, mcp/machine backends, Firebase preview channel) now ask GitHub whether the PR is still open right before deploying and skip when it's closed, and ask again after deploying and delete what they created if it closed meanwhile (new action `platform-action/pr-closed`; the reusable workflows now request `pull-requests: read`). A concurrency group can't fix this: a merged PR's `closed` run gets the base branch as `github.ref`, and the cleanup starts minutes before the deploy jobs reach the deploy.
- The platform's PR-close cleanup now passes `config_path` on to `_cleanup-preview.yml`.
- **Bootstrap signed-URL IAM permission** (#35) — the platform CI/CD service account is now granted `roles/iam.serviceAccountAdmin` during bootstrap so the keyless V4 signed-URL IAM binding can be applied to buckets declared under `storage.buckets`. Resolves a bootstrap failure that occurred when a `storage.buckets` block was present.
